## Structural hold audit and race boundaries

The direct update/done/fail gate is materially stronger. Done's expensive planning happens before the locked mutation, but `agentMutate` rereads the row and its question summary under `s.mu`, so an existing hold added during that planning is seen. Delegation checks a resolved parent's current holds under the same lock before inserting (`delegate.go:171–179`), rather than trusting the earlier parent snapshot. Ordinary runtime row updates go through `mutate`; the direct save callers in `protocol.go:140` and `adopt.go:82` are creation paths, and `demo_accept.go:40` is explicitly demo state.

The report's claim that *every* agent verb goes through `agentMutate` is not literally true. Hooks and tool activity use ordinary mutations; question-derived state is changed directly in `service.go:534–546`, not lifted through `liftHoldLocked`, and `HoldQuestions` is supplied dynamically by `effectiveHolds`. `liftHoldLocked` accepts a lifter label for journalling but does not enforce that label against `Hold.Lift` (`holdset.go:189–210`); correctness depends on each caller. Terminal states clear all holds in `applyHoldsLocked`, and holds are intentionally latent during checking/reviewing, so “every write reapplies holds” is not equivalent to “every continuation/terminal transition is blocked.” R7-C02 through C05 are the concrete consequences found; this is not a claim that every unsound-looking path has a demonstrated exploit.

Recovery preserves serialized holds and migration 0019 backfills the principal old gates. It does not repair interrupted descendant propagation. `retry` can lift usage-limit holds on observed working activity (`recovery.go:399–407`), so an agent already doing tools can cause recovery to clear that disposition without a human; that is an explicit recovery policy, not proof of an unbypassable execution stop. The holds constrain the protocol and automatic control, not same-uid processes or arbitrary tools.

## Acceptance details

There is no clean-copy implementation to inspect on this pinned commit. Submodules, LFS, ignored artifacts, hooks/filters and project dependencies therefore remain the live checkout's inputs; cleanliness before/after cannot attest to their immutable identity or to transient tracked edits. Command discovery also reads the live checkout (`accept.go:188–206`). `checkEnv` removes named credential/agent variables but otherwise inherits environment and appends extras without re-filtering (`:485–503`); this is useful credential reduction, not a reproducible environment.

Recheck now shares Done's clean-tree prerequisite, but does not call the complete `planAccept`: Done also requires a no-commits explanation when an isolated branch is not ahead (`accept.go:247–249`), whereas Recheck checks allowed state, clean tree and command (`:738–773`). A finished job already supplied a result, so this distinction is not counted separately as a release defect. Ordinary nonzero exits and persistence failures do not accept; unavailable snapshots go to errors. No fallback-on-copy-failure claim is valid because a copy is never attempted.

## Freshness, startup, browse and diff qualifications

- The fingerprint excludes the per-start token, normalizes the build version and hashes deterministic JSON (`freshness.go:45–70`); its KV record persists across crowsnest restart. No unconditional timestamp-driven restart loop was found in the production composition inspected. The ten-minute restart backoff itself is process-local (`:119,139,151`), so it is not a persistent cross-restart rate limit.
- Automatic refresh checks pause, ready status, lifecycle activity of a held job, dialog and draft before stopping (`freshness.go:132–157`). `HeldJobBusy` only tests `LifecycleOp`, not all held states (`cmd/crowsnest/upkeep.go:239–254`). These are sampled readiness checks, not an atomic reservation against all pane writers or an external terminal user; no live concurrency validation was permitted. The notice-delivery failure in C11 is concrete even without a pane timing race. Codex standing agents have no SessionStart notice transport; resumed-instruction behavior for them is not established by the Claude journey.
- Early HTTP answers every request 503 with Retry-After and never dispatches a mutation (`httpd/server.go:432–458`). It does not queue/replay writes. Hooks use the separate agent socket (`cmd/crowsnest/jobs.go:365–405`), not these listeners: ordinary hook failures print nothing and are deliberately fail-open; PermissionRequest falls back to Claude's own decision UI, and PreToolUse runs the local rules. Thus STARTING is not a durable buffer for live-agent hook events or instruction context. Failed Stop observation can be recovered by the backstop; a missed notification/session instruction is not equivalent to a persisted event.
- Browse List/Facts/Favourites use a buffered completion channel and retain a slot until a stuck worker actually returns (`browse.go:263–295`): four permanently stuck reads exhaust this service, but do not create unlimited workers on these paths. C10 is the separate unbounded route. `List` reads the entire directory before applying the 500-entry cap (`list.go:93–115`), so that cap is not a directory-size/memory bound. Root admission resolves symlinks; this is still check-then-use, not fd-relative race-proof containment. Metadata `ReadFile` opens before checking regular-file type (`fs.go:50–63`), so a planted FIFO can strand a bounded slot.
- Normal diff hashes include both blobs, paths and changed modes (`landing/changes.go:405–408`) and are compared across scopes (`changes.go:569–576`); committing unchanged content does not inherently erase Viewed. Skipped files use size/mtime instead of a content digest (`landing/changes.go:326–327`), so touching unchanged content clears those marks and same-size/same-mtime replacement can preserve them. LFS filters are disabled for WorkTree, so raw materialized LFS content is not necessarily comparable with the committed pointer representation.
- SSE does not directly self-loop: only `job` events schedule reads (`changes.go:1030–1032`), reads are throttled, and unchanged fingerprints do not publish (`:263–279`). Multiple subject/base entries, queued timers and large reads still have the resource/cache limits in C09. No browser performance or large-repository timing measurements were performed.
- The real-Claude task still omits the enabling variable (`mise.toml:156–159`), while the rig skips without it (`web/e2e/claude/rig.ts:24`). A nominal successful `mise run e2e:claude` alone does not prove those journeys ran. The reports distinguish explicit-variable runs; none is independent validation by this reviewer. Theme/manual reports and relevant integration claims were consulted, but this was not a visual/accessibility audit of every view or a full reread of every manual page.

Main at `3456e19` is not fit to tag as a release with the claimed acceptance and hold guarantees. Close the live-worktree evidence gap and the budget/continuation recovery holes, then fix the new Viewed gate and concurrency defects before treating the added UI as a dependable review boundary. Run the required gate and targeted crash/race/large-repository scenarios on the resulting exact commit, including explicitly enabled real-Claude journeys; this read-only review supplies no passing test result.
