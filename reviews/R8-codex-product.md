## devtun: integrate the experience, keep the transport separate

**Yes to previews and a shared place to notice approvals. No to merging the two daemons.** Crowsnest already recognizes devtun's browser-opening shim in `internal/opener/opener.go`; extend that cooperation. devtun owns SSH reconnects, port mappings, host keys, 1Password policy, signing and the laptop agents. Crowsnest owns job identity, results, attention and evidence. Their lifetimes differ: bedev jobs survive a closed laptop; access to an unlocked laptop vault does not magically survive with them.

For previews, register a selected HTTP service against a job and checkout, not “every listening port is now reachable from the phone.” On bedev, the crowsnest instance can front that service directly; it need not route through the sleeping laptop. On the desktop it can also link through devtun's existing mapping. Include HTTP/WebSocket support for live reload, explicit readiness, expiry, and teardown. **2–3 days for a constrained prototype; several more for robust exposure across real apps.**

**Do not serve agent-authored HTML under crowsnest's own origin.** A path such as `/jobs/12/preview/` does not isolate scripts from the cockpit's authenticated APIs. Use a separate origin and narrowly scoped, expiring preview authentication; do not forward cockpit cookies, Authorization or Tailscale identity headers upstream. Different ports alone do not isolate cookies. Restrict upstream destinations and redirects, bound connections, and revoke a registration when its process/port ownership changes so an old link cannot expose a replacement service. Keep database/debug/admin ports private. A separate origin adds certificate/routing work: authenticated links to an existing preview service are a sensible first delivery while that boundary is built.

For secrets/signing, first show a devtun-origin attention card with host, account/key, purpose, expiry and **Open in devtun**. A later bridge may answer a particular request, but devtun must remain the policy authority: request ID/input binding, one-use settlement, expiry, revocation, first-answer-wins, and no “remember” grant silently widened by crowsnest. Never copy secret values into job transcripts or its database. A crowsnest login must not automatically become permission to use the laptop vault. Show **Laptop approver unavailable** when it sleeps. **A day** for a small read-only integration if a suitable event API exists; **days** for an authenticated answer bridge, which this README inspection does not establish already exists.

The strongest argument against integration is real: previews and vault approvals enlarge the attack surface of a cockpit whose agents share its OS user. That argues for narrow adapters and separate authority, not for leaving you to juggle unrelated windows forever.

## If I had one week

1. **Day 1: prove and simplify the phone loop.** Real installed phone, background push, answer, resume, result and reconnect; fix failures. Cap Now's initial queue, simplify rescue and label Codex honestly. Record failures as failures. Publication/testing authority is a separate operational step.
2. **Days 2–3: make one result runnable from its job.** Start with an explicit, already authenticated preview URL plus revision/readiness. Prove one safe separate-origin route if feasible; do not rush an arbitrary proxy into those two days. The success is trying the Website change from the phone.
3. **Days 4–5: keep one delivered change accountable after push.** Start with Azure DevOps for Barreleye: truthful push labeling, attach a PR URL, poll its CI/review state read-only, and propose a linked repair job. Leave PR creation and automatic comment ingestion for the next increment if provider integration consumes the time. Push remains a human action.

The single thing that changes the feeling most: **a finished job opens to “here is what changed; try it; here is the evidence; here is the next decision.”** The transcript and terminal remain available, but the result becomes the center of the experience.
